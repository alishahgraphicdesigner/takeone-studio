# UI Responsiveness & State Sync Audit — TakeOne Studio v2.2.0
**Date:** 2026-10-16
**Auditor:** Subagent (deep audit)
**Scope:** `renderer/models.js`, `renderer/models.css`, `renderer/studio.html`, `preload.js` (+ backend touchpoints in `main.js`, `main/downloads.js`, `main/deps.js` where they affect UI behavior)
**Method:** Static code review, tracing event flows, simulating fast clicks / slow machine / flaky network.

**Assumption:** The user clicks fast, the machine is slow, the network drops. Every finding below is a real defect under those conditions, not a theoretical nit.

---

## CRITICAL (breaks interaction or corrupts state)

### C1. `INSTALL_START` is recreated empty on every `renderDock()` — elapsed time never works
- **File:** `renderer/models.js:199` — `const INSTALL_START = {};` is declared **inside** `renderDock()`.
- **What's wrong:** Every call to `renderDock()` (which happens on every throttled refresh, ~every 800ms while active) creates a brand-new empty object. The elapsed-time logic at lines 204–210 does `INSTALL_START[t.id] || Date.now()` — since the object is always fresh, this is always `Date.now()`. Elapsed time permanently reads "0s"–"1s" and the 10-minute "still working" reassurance at line 220 can **never** trigger.
- **Why it matters:** The feature was added to answer "is this install stuck?" — it silently does nothing. Worse, it looks like it works in a quick manual test (shows "· 0s") but never accumulates.
- **Fix:** Move `const INSTALL_START = {};` to module scope (next to `let STATES = {}` at the top of the IIFE), so it persists across renders. Delete entries when installs complete/fail/cancel.

### C2. Full `#modelCards` re-render on every refresh destroys in-flight UI state
- **File:** `renderer/models.js:160-161` — `host.innerHTML = suggestions() + groups();` inside `refreshStates()`, which runs on every throttled progress event (~every 800ms while anything is active).
- **What's wrong:** This replaces **every card**, not just the dock. Casualties on each re-render:
  - An open "Why?" box (`#why-<id>`, toggled by `act('why')`) is destroyed — the user's open explanation vanishes mid-read.
  - The Verify button's `disabled = true` state (set in `act('verify')`, line 271) is wiped — a re-created **enabled** button appears while verification is still running.
  - The `#verify-<id>` note span is destroyed and recreated empty; the async verify completion then writes into the *new* element, which works, but any "Checking…" indicator the user saw is gone.
  - Hover/focus states on all buttons are lost; keyboard focus is dropped (accessibility + keyboard users).
  - Scroll position *within* the cards area is preserved (page scroll, not inner), but any element-level state is gone.
- **Why it matters:** The user experiences the UI as "flickery and forgetful." The Verify double-run is the sharpest edge (see C3).
- **Fix:** Split rendering: re-render `#modelCards` only when the *set* of states changes in a way that affects cards (state transitions), and update only progress bars / labels in place on progress ticks. At minimum, preserve `whybox` open state and verify-button disabled state across renders (e.g., snapshot `document.querySelectorAll('.whybox:not([hidden])')` ids before render and re-open after; track a `VERIFYING = Set()` of ids and re-disable).

### C3. Verify can double-run (button-disable defeated by re-render)
- **File:** `renderer/models.js:270-272` (`btn.disabled = true`), defeated by C2's re-render at line 161.
- **What's wrong:** `act('verify')` disables the button, awaits `verifyTool` (which can take seconds — it stats files and hashes). If a progress event fires during the await, `refreshStates()` re-creates the card with a fresh **enabled** Verify button. A fast user clicks again → two concurrent `verifyTool` IPCs for the same tool. Both write to `#verify-<id>`; last writer wins, and the button text may end up inconsistent ("Check again" vs "Verify").
- **Why it matters:** Wasted I/O (hashing multi-GB files twice), confusing note text, and it trains the user that buttons need multiple clicks.
- **Fix:** Guard in `act()`: `if (VERIFYING.has(id)) return; VERIFYING.add(id); ... finally VERIFYING.delete(id)`, independent of DOM state. Or disable via a state flag consulted by `actionFor()`.

### C4. `depInstall` has no idempotency guard — double-click queues two installs
- **File:** `main.js:978` (`takeone:depInstall` handler). Compare `addDownload` in `main/downloads.js:202-205`, which *does* guard (`Already downloading.`).
- **What's wrong:** Rapid double-click on Install (easy on a slow machine where the first click shows no immediate feedback — the optimistic `refreshStates()` at `models.js:259` is throttled up to 800ms) fires two `depInstall` IPCs. Both increment `installQueueDepth`, both set status `queued`, both enter `queueInstall`. The tool gets installed **twice** sequentially — second pip run is pure waste (minutes), and for `hf` tools it re-downloads.
- **Why it matters:** Directly wastes the user's time on multi-minute installs; also corrupts the queue-depth display.
- **Fix:** In the `depInstall` handler, check current status first: if `ts.status` is `queued`/`installing`, return `{ ok: false, reason: 'Already queued.' }`. Also disable the Install button optimistically in `act()` (set a pending flag) until the IPC returns.

### C5. Backend progress emits every 500ms unconditionally while downloading — re-render storm
- **File:** `main/downloads.js:16` (`POLL_MS = 500`), `main/downloads.js:302-305`.
- **What's wrong:** The emit condition is `if (uiState !== e.status || Math.abs(progress - (e.progress || 0)) > 0.004 || uiState === 'downloading')`. The trailing `|| uiState === 'downloading'` means **every 500ms poll emits a `dl-event` while any download is active**, even if nothing changed (0 bytes received on a stalled connection). Each event crosses IPC and triggers `refreshStates()` in the renderer.
- **Why it matters:** The 800ms throttle (C6) caps the damage, but the pipeline is still: 500ms IPC event → throttle → 800ms full `toolStates()` IPC round-trip + full DOM re-render. On a slow machine this is constant jank; it also keeps the machine awake and burns CPU for zero information. It is the *root cause* of the "buttons need 3–4 clicks" bug the throttle only mitigates.
- **Fix:** Remove the `|| uiState === 'downloading'` clause. Emit on actual change only (state change, ≥0.4% progress delta — already there). Add a separate low-frequency heartbeat (e.g., every 5s) *only* to update speed/elapsed displays, and make the renderer update those in place without a full re-render.

### C6. The 800ms throttle mitigates but does not fix the click-eating re-render
- **File:** `renderer/models.js:143-158`.
- **What's wrong:** The throttle reduces re-render frequency, but the fundamental race remains: `dock.innerHTML = html` (line 235) and `host.innerHTML = ...` (line 161) still destroy the exact button element between the user's `mousedown` and `mouseup`. With an 800ms re-render cadence and a ~100–200ms click, the collision probability per click is ~15–25% — down from near-certain, but the user will still lose roughly 1 in 5–6 clicks during active downloads. The user's report ("3–4 presses") is consistent with the *unthrottled* storm; the throttle improves it to "occasionally needs 2 presses," which will read as "still broken."
- **Why it matters:** Partial fix for the #1 user complaint. Trust is not restored by "better odds."
- **Fix:** Never replace button elements on progress updates. Render the dock/cards once per *state transition*; on progress ticks, update only `.prog i` widths, `.st` text, and `.progwrap` labels via targeted DOM queries (`dock.querySelector('[data-id="x"] .prog i')`). Reserve `innerHTML` for structural changes (tool added/removed from the active set, state class change).

## HIGH (wrong information, dead ends, or significant UX breakage)

### H1. No polling fallback — UI goes permanently stale if an event is missed
- **File:** `renderer/models.js:304-305` (event-only refresh).
- **What's wrong:** `refreshStates()` runs only on `dl-event`/`dep-event` and after user actions. There is no timer-based refresh. If an event is dropped (IPC hiccup, backend emitted before the renderer subscribed, watchdog restart gap), or if the backend reaches a terminal state through a path that doesn't emit (e.g., `fail()` catch paths that only `persist()`), the UI shows the old state **forever** — "Downloading 45%" on a dead download, "Installing…" on a finished install.
- **Why it matters:** On a flaky network with daemon restarts, this is not hypothetical. The user cannot distinguish "stuck UI" from "stuck download" and will hammer buttons.
- **Fix:** Add a slow safety poll: `setInterval(() => { if (document.getElementById('view-models').classList.contains('on')) refreshStates(true); }, 15000)` — bypass-throttle variant, cheap, only when the Models view is visible.

### H2. Pip progress jumps backwards (per-file %, not overall)
- **File:** `main/deps.js:39-44` (`parsePipProgress`), surfaced at `renderer/models.js:201`.
- **What's wrong:** `parsePipProgress` scrapes `(\d+)%` from pip's stderr. Pip reports % **per file being downloaded**, resetting to 0 for each new file. A 12-package install shows 0→100→0→100… The dock progress bar visibly jumps backwards, and the `%` label contradicts the "Installing packages…" phase text.
- **Why it matters:** The user asked for install % to trust progress; a backwards-jumping bar destroys that trust and looks like a bug.
- **Fix:** Track package index: parse `Collecting <pkg>` / `Downloading <pkg>` lines to count completed packages vs total where knowable; otherwise show phase + elapsed + an *indeterminate* bar (CSS animation) instead of a lying % — or clamp the displayed % to never decrease (monotonic).

### H3. `dlStart` "Already downloading" reason is swallowed
- **File:** `renderer/models.js:250` — `await window.takeone.dlStart(id, ROOT);` return value ignored.
- **What's wrong:** `addDownload` correctly returns `{ ok: false, reason: 'Already downloading.' }` on double-click, but `act('download')` never checks it. The user gets silence. (Install path at line 262 *does* check and `notice()`s.)
- **Why it matters:** Inconsistent feedback; double-click on Download appears to do nothing (or worse, the user thinks the first click didn't register and keeps clicking).
- **Fix:** Mirror the install path: `const r = await window.takeone.dlStart(id, ROOT); if (!r.ok && r.reason) notice(r.reason);`

### H4. Error card text is wrong for downloads ("Nothing was installed")
- **File:** `renderer/models.js:67-70` (`errorFor`).
- **What's wrong:** The template hardcodes "Nothing was installed. You can try again — no files were left half-written." For a **download** failure, nothing was being *installed*; the file may well have been left half-written in staging (that's the point of resume). Both claims are false for the download path.
- **Why it matters:** The user reads a reassurance that contradicts what they see (a multi-GB partial file on disk), eroding trust in all honest messaging.
- **Fix:** Branch on `tool.installType === 'file'`: "The download didn't finish. Your partial download is kept — Try again resumes where it stopped." Keep the install wording for pip/hf.

### H5. Raw aria2c jargon leaks into the FAILED card (".aria2", "--allow-overwrite=true")
- **File:** `main/downloads.js` (error propagation from `st.errorMessage`), rendered raw at `renderer/models.js:69` via `esc(st.error)`.
- **What's wrong:** The user-facing card shows: *"File …gguf exists, but a control file(*.aria2) does not exist… add --allow-overwrite=true option and restart aria2."* This is daemon-internal vocabulary and a CLI flag the user can never act on. It also contradicts the product promise ("nothing here needs a terminal").
- **Why it matters:** The single most-seen error in the current session is incomprehensible. The user cannot self-serve.
- **Fix:** Map known aria2c error signatures to plain-words messages in `fail()` before persisting: e.g. `/control file.*\.aria2.*does not exist/` → "The download's resume data was lost, so it can't continue safely. Try again starts it fresh." Never surface flags/paths internals.

### H6. Dock content padding is fixed 432px — breaks on narrow windows
- **File:** `renderer/models.css:76` — `body.dock-open #view-models{padding-right:432px}`; dock is `width:400px; max-width:calc(100vw - 32px)` (line 53).
- **What's wrong:** On a ≤900px-wide window the dock's `max-width` shrinks it (e.g., 768px dock on an 800px window) but the padding stays 432px, leaving ~168px for cards whose grid minimum is 280px → horizontal overflow / crushed layout. The 432px also assumes the 400px width + 32px margins exactly; any scrollbar or OS chrome breaks the alignment.
- **Why it matters:** Small laptop windows and snapped-half-screen (a realistic office scenario) get a broken Models page whenever the dock is open.
- **Fix:** Make the padding track the dock: `body.dock-open #view-models{padding-right:min(432px, calc(100vw - 320px))}` and add `@media (max-width:760px){ .dock{left:16px; width:auto} body.dock-open #view-models{padding-right:0} }` (overlay mode on small screens, since reflow is impossible).

### H7. Queued installs show Cancel, but queued *downloads* show nothing actionable in the dock
- **File:** `renderer/models.js:224-231` (`ops` builder).
- **What's wrong:** `ops` covers `downloading`, `paused`/`interrupted`, `installing`/`queued` — but a download in `queued` state (behind the 3-download limit) matches **none** of the branches (first branch is `downloading` only; second is `paused`/`interrupted`; third is `installing`/`queued` → renders `install-cancel`, which calls `depCancel` — the **wrong** backend for a download!). A queued download therefore gets an **Install-Cancel button that calls the pip-cancel IPC**, which will no-op or, worse, touch `installCancels[toolId]` state for a download.
- **Why it matters:** Wrong action on a visible button; canceling a queued download is impossible from the dock (must wait or use the card, where `actionFor` has no `queued` case either — falls through to `default` → shows Download/Install again, also wrong).
- **Fix:** Split `ops` by tool kind: downloads (`dlStates` incl. `queued`) get `data-act="cancel"` (dlCancel); installs get `data-act="install-cancel"`. Add explicit `queued` handling in card `actionFor()` too.

### H8. `act('install')` optimistic refresh is throttled — "queued" feedback delayed up to 800ms+
- **File:** `renderer/models.js:257-262`.
- **What's wrong:** The comment says "Refresh right away so a queued position shows instead of silence," but `refreshStates()` at line 259 goes through the 800ms throttle. If a progress event just fired, the optimistic update waits the full remainder. On a slow machine the user sees *nothing* for ~1s after clicking Install — the exact dead-click feeling that prompts double-clicks (→ C4).
- **Why it matters:** Directly feeds the double-click → double-install loop.
- **Fix:** Add a bypass parameter: `refreshStates(true)` for user-initiated actions, skipping the throttle (user actions are rare; progress storms are not).

## MEDIUM (polish, correctness, robustness)

### M1. Progress shows 100% prematurely (`Math.round`)
- **File:** `renderer/models.js:61` (card), `:201` (dock).
- **What's wrong:** `Math.round(0.996 * 100)` = 100% while the file is still downloading/verifying. The bar sits at full for the entire verify phase, then the card flips to Installed — the user never sees completion *happen*.
- **Fix:** `Math.floor` for in-progress states; show 100 only on terminal `done`. Or reserve the last 2% for verify.

### M2. `body.dock-open` is not cleared when leaving the Models view
- **File:** `renderer/models.js:167-168` (cleared only when `active.length === 0`).
- **What's wrong:** If the user switches to Studio/Library while downloads run, `body.dock-open` stays set. It's scoped to `#view-models` so it's visually harmless today, but any future global style keyed on `dock-open` (or a second consumer) inherits a lie. Also `renderDock()` keeps running (and re-rendering a hidden dock) on every background event — wasted IPC + DOM churn.
- **Fix:** In `renderDock()`, early-return (skip DOM work) when `#view-models` is not `.on`; and remove `dock-open` when the view hides (hook the view-switch in `ui.js`/`studio.js` or a MutationObserver).

### M3. Minimize/FAB wiring is inconsistent and order-fragile
- **File:** `renderer/models.js:181-193`.
- **What's wrong:** (a) `minBtn.onclick` is re-assigned on every render while the FAB uses a `dataset.wired` once-guard — two conventions for the same job. (b) The minimize handler references `count` (line 188) which is declared at line 193, *after* the handler is defined — works only because the closure runs later; a future refactor that inlines the call breaks it silently. (c) If `renderDock()` runs while minimized (it force-removes `minimized` at line 172 every render!), a minimize is undone by the next progress event — the user's minimize lasts <800ms.
- **Why it matters:** (c) is user-visible: minimize the panel, it pops back open on the next tick. The user asked for minimize to *get it out of the way*.
- **Fix:** Persist minimize intent in a module-scope `let dockMinimized` flag; `renderDock()` respects it instead of force-clearing. Hoist `count` above the handlers.

### M4. Unused `isDl` variable; dead code in `rowHtml`
- **File:** `renderer/models.js:211` — `const isDl = dlStates.includes(st.state);` never read.
- **Fix:** Delete (it was presumably meant for H7's split).

### M5. `speed` shows "· stalled?" for any 0-Bps downloading state
- **File:** `renderer/models.js:213-215`.
- **What's wrong:** `st.state === 'downloading' && speedBps === 0` renders "0% · stalled?" — including the first 1–2s of a healthy download (connection setup) and every trackerless pause. The UX audit already flagged "stalled?" as anxiety-inducing wording; it's also *wrong* half the time.
- **Fix:** Only show "stalled" after N seconds of zero throughput (track `lastBytesAt` per tool in module scope); before that show "Connecting…".

### M6. Event listeners accumulate if `wire()` ever runs twice
- **File:** `preload.js:50-51` — `onDlEvent: (cb) => ipcRenderer.on(...)` adds a listener per call; `renderer/models.js:304-305` calls it in `wire()`.
- **What's wrong:** Today `wire()` runs once, so it's latent. But there is no guard: any future re-init (HMR, view re-creation, bugfix calling `init()` again) doubles every handler → double `refreshStates()` per event → double IPC load and double throttle timers.
- **Fix:** In preload, use a set-once pattern or `ipcRenderer.removeAllListeners('dl-event')` before adding; or guard `wire()` with a module flag.

### M7. `refreshStates()` catches IPC failure by keeping stale STATES silently
- **File:** `renderer/models.js:155-157` — `catch { /* keep old */ }`.
- **What's wrong:** If `toolStates()` throws (main process busy, root unreachable), the UI keeps rendering the *previous* snapshot with no indication it's stale. Combined with H1, the user can stare at a frozen-but-confident UI.
- **Fix:** Track consecutive failures; after 2, show a subtle "Couldn't refresh — retrying…" marker in the dock header or offline banner area.

### M8. The dock has no `aria-live` / focus management; `role="progressbar"` values go stale between renders
- **File:** `renderer/models.js:232-234`, `renderer/models.css`.
- **What's wrong:** Progressbar `aria-valuenow` is only correct at render time; screen-reader users get no announcements of state transitions (failed, done). Minor vs. the interaction bugs, but the roles are already half-implemented — finishing is cheap.
- **Fix:** Add `aria-live="polite"` to the dock status column; announce terminal transitions via a visually-hidden live region.

### M9. `#dockFab` is inside `#view-models` but positioned `fixed`
- **File:** `renderer/studio.html:46`, `renderer/models.css:71-74`.
- **What's wrong:** Works today (hidden with the view), but it's conceptually a global control positioned against the viewport. If the dock is ever moved out of the Models view (e.g., to be visible app-wide), the FAB's `hidden` management in `renderDock()` (which only runs from Models refreshes) desyncs.
- **Fix:** No action needed today; note for the planned app-wide activity panel.

### M10. `notice()` calls in `act()` rely on a global from `ui.js` load order
- **File:** `renderer/models.js:256,263,291`; `renderer/ui.js:26`.
- **What's wrong:** `notice` is `window.notice` set by `ui.js`. `studio.html` loads `ui.js` before `models.js`, so it works — but it's an implicit cross-file dependency with no guard. If script order changes or `ui.js` fails, every error path in `act()` throws `notice is not defined`, masking the real error.
- **Fix:** In `models.js`, `const notice = window.notice || ((m) => alert(m));` — degrades honestly.

## What the throttle did and didn't do

The 800ms throttle (`models.js:143-158`) reduced the *frequency* of the click-eating re-render but left the *mechanism* intact. Expected residual: ~1 lost click in 5–6 during active transfers (800ms render cadence vs ~150ms click). The durable fix is C6: stop replacing buttons on progress ticks; update widths/labels in place.

1. **C6** (in-place progress updates) — kills the click bug class, not just this instance.
2. **C1** (hoist `INSTALL_START`) — one-line, makes elapsed time real.
3. **C4** (depInstall idempotency) + **H8** (bypass throttle on user actions) — ends double-installs.

6. **H7** (queued-download cancel action) — wrong-button bug.

8. **H1+M7** (15s safety poll + stale marker) — bounds every sync failure.
9. Remainder (M1, M2, M3, M5, M6, M8, M9, M10) as hardening.
